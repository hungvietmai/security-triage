# Evaluation on pairs-v1: status and what is missing

**Status on 2026-11-14: not run. No pair of pairs-v1 has been scanned by the v0.2 pipeline,**
except `curling@0.2.0`, whose prior exposure the manifest already records. This directory holds
the scoring kit, so that the run needs no new code, and the exact list of what blocks it.

## Why it is not run

| # | Blocker | Where the rule is | Who can lift it |
|---|---|---|---|
| 1 | The held-out split (16 pairs) can be opened once. Before any held-out run the protocol requires a commit of the protocol and amendments, the split, the exact tool versions, rule and query hashes, the policy version, the development effort log and the frozen configuration manifest; a run is blocked when any item is missing | [EVALUATION_PROTOCOL.md §7](../../EVALUATION_PROTOCOL.md) | The project owner |
| 2 | The v0.2 profile, the filter rules (`adjudicate-v0.2`) and both evidence packs exist only in the working tree; the owner asked to keep changes local. No development effort log covers them | `git status`; [docs/thesis/PROGRESS.md](../../../docs/thesis/PROGRESS.md) | The project owner (commit and push) |
| 3 | The locked archive cache `artifacts/pair-sources/` is not on this machine. Missing cache bytes stop the workflow, and a new download is not a substitute for locked bytes | [pairs/README.md](../../pairs/README.md) | The project owner (restore the cache from its backup, or amend the rule) |
| 4 | The development split (34 acquired pairs, never scanned) is not gated by §7, but agents must not run scanners on frozen pairs to validate tooling, and a first scan cannot be undone | [experiments/AGENTS.md](../../AGENTS.md) | The project owner |

Blocker 3 has a possible technical answer that still needs the owner's decision: the application
records the SHA-256 of the archive it scans, and for `curling@0.2.0` that hash equals the one in
`sources.lock.json`. A scan through the application can therefore be checked against the lock
(`pair_labels.py --verify`). npm archives are verified against the registry's integrity hash;
GitHub archives are regenerated by GitHub and may no longer match.

## What the owner has to do to run it

1. Decide whether to open the held-out split for the v0.2 pipeline (docs/research.md, open item 7).
2. Commit and push, in this order and before any scan: the v0.2 profile and code; an amendment
   that fixes the question, the configurations compared, the counting unit, the matching rule
   and the reading of each outcome. [../independent-secbench/PROTOCOL.md](../independent-secbench/PROTOCOL.md)
   sections 3 to 6 can be reused as its text.
3. Restore `artifacts/pair-sources/`, or record in the amendment that sources are re-acquired
   through the application and accepted only when `--verify` reports the locked bytes.
4. Build the labels, scan each vulnerable version once, verify, score:

```bash
python experiments/evaluation/pairs-v1/pair_labels.py held_out --json <run-dir>/labels.json
# scan every source of <run-dir>/labels.json once with profile command-injection-v0.2,
# saving the exports to <run-dir>/inputs/<pair id>/ (see ../independent-secbench/collect.py)
python experiments/evaluation/pairs-v1/pair_labels.py held_out --verify <run-dir>/inputs
python experiments/evaluation/independent-secbench/configurations.py \
  <run-dir>/labels.json <run-dir>/inputs --json <run-dir>/results.json
```

## What the run can and cannot show

| Split | Pairs acquired | With a resolved known location | Language of the resolved ones |
|---|---:|---:|---|
| development | 34 | 26 | 21 JavaScript, 5 Python |
| held_out | 16 | 9 | 8 JavaScript, 1 Python |

- It gives coverage of known vulnerable locations per configuration, lost true positives and
  the priority of each known location, on real CVEs.
- It gives **no precision**: the fixed version is not a negative label (pairs/README.md), and
  candidates outside the known location are unlabeled.
- The held-out split has one resolved Python location, so it says almost nothing about the
  filter step, which only has evidence packs for Python.
